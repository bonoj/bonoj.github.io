# I. INVITATION TO THE GRAND OPENING

Welcome to EVERMORE GAMES, a completely fictional, splendidly overfunded mobile gaming empire. Every title is breathtakingly familiar. Every decision is correct. Every tap is rewarded. Every economy is simultaneously overflowing with wealth and experiencing a critical shortage of one more currency.

The flagship, **MATCH 1™**, removes the inconvenient requirement to match three things. One tap suffices. Its sequel, **MATCH 0™**, has removed the tap as well. Our shareholders regard this as a breakthrough in consumer convenience. Our scientists have established that a 100% success rate can be improved by 15% without altering it.

This is **beautifully banal** by design: gorgeous jewel-toned mobile-game language, glossy prizes, gold-trimmed UI, triumphant animations, frictionless fictional progression, and an ever-expanding structure of rewards for rewards for rewards. The comedy lies in systems that take their own nonsense with impeccable seriousness. There are **no real-money purchases, payment processing, genuine investment products, or actual gambling**. The satirical economy is local to the browser.

**Ceremonial proclamation:** The player is our most valued customer, shareholder, monarch, student, taxpayer, particle employer, defendant, creditor, and entirely voluntary subject. Tiffany thanks you for your service.

## Flagship: MATCH 1™

**Player action:** tap a jewel. **System response:** victory, score, currency rewards, praise, particle spectacle. Its deliberately trivial input is the seed of the entire interinstitutional chain: a match can create stars and coins; rewards can become ledger events; events can move securities and research; celebrations can manufacture particle records; particles can be reclaimed and taxed; legal disputes can generate still more ceremonies. The original puzzle is the smallest possible ignition switch for the largest possible bureaucracy.

**Lore:** In the first age, citizens matched three gems. In the second age, they matched one. In the promised third age, matching will be prohibited as unnecessary user friction. A university department is investigating whether zero taps constitute a negative tap.

**Future:** gemstone botanical classification; 128-stage victory combos; royal sponsorship of individual gems; gem-specific unions; gem ancestry; a competitive ranking system in which all players share first place; a spectator mode that congratulates observers for watching.

## Kingdom Eternal

The royal realm contains buildings, upgrades, and civic pride. Its rulers are subject to planning permits, appreciation assessments, royal builder-protection law, and competing claims from Tiffany's cabinet. Future building permits should feed Parliament, taxes, securities, and the cross-game supply chain.

## Faction Wars

Conflict is guaranteed to produce glory. Every faction may be sovereign, but all factions ultimately belong to the same parent company. Future diplomacy will allow sanctions on one's own kingdoms, followed by humanitarian relief paid from the same treasury.

## Merge Forever

Dragon eggs are both pets and speculative financial instruments. Every hatch could create a genetic record, a new royal claimant, a stock-market movement, and an insurance event. The Dragon Egg Index must never become less exciting merely because no dragon has actually hatched.

## Frozen Throne

Warmth is a strategic commodity. A snowstorm should influence heat production, the Weather Bureau, and the warmth securities market. Future treaties may require players to declare their winter preferences to a multinational climate commission chaired by Tiffany.

## Hero Ascension

Heroes do their own work. Players are praised for allowing it. A future Labor Ministry should classify idle heroes as both employed and on vacation, making them simultaneously eligible for wages, vacation pay, and retirement.

## Royal Renovation

The mansion is an appreciating asset and a never-ending aesthetic obligation. Every new wallpaper pattern should increase property value, trigger reassessment, and require a royal inspection.

## Treasure Tycoon

Wealth accumulates because accumulation is its own justification. This is the natural home for stock exchange settlement, Royal Reserve audits, sovereign wealth bonds, and increasingly intricate fictional bookkeeping.

## Island Paradise

Islands produce resources, which justify boats, which justify customs, which justify international maritime law, which justifies an entirely new currency. The future Island Customs Authority must be a delightfully inefficient branch of the shared logistics system.

## Galaxy Dominion

Space is enormous, but paperwork scales better. Planets may declare independence, be acquired by Evermore Parent Holdings, and continue to receive the same Tiffany tutorial. Future interstellar settlement can take place in Tomorrow Tokens.

## Pet Champions

Affection is both a feeling and a financial instrument. Companion Bonds, Friendship, Loyalty, Admiration, and Tiffany Favor are all plausible denominations in a civilization that insists on measuring devotion.

## Match 0

A sequel that has won before opening. It is the ideal site for retroactive achievements, Yesterday Credits, paradox tax, and a Causality Tribunal. **Its highest possible victory animation should play before the user arrives.**

# IV. THE EVERMORE SHARED GRAMMAR

1. **One empire, twelve doors.** The catalog is not a collection of unrelated prototypes; it is one corporate identity with a consistent language.
2. **Instant legibility.** A player should understand the immediate action without reading a manual.
3. **Victory is the default.** Friction is largely ceremonial. The joke is overabundance, not cruelty.
4. **Every reward has provenance.** Currency, event, achievement, and celebration should eventually be traceable to a concrete action.
5. **Every screen is a department.** Distinct thematic flavor, shared visual vocabulary.
6. **Every institution creates dependencies.** A new system should interpret old events, not merely sit beside them.
7. **Tiffany is everywhere.** Tutorial guide, finance minister, monarch, university chancellor, wedding officiant, judge, and institutional continuity.
8. **Local, fictional, reversible.** No real purchases, personal financial data, external accounts, or manipulative real-world scarcity.
9. **Mobile first.** Comfortable thumb targets, single-column fallbacks, scrollable horizontal navigation, no page-level sideways overflow.
10. **Particles are serious business.** Spectacle has an economy, and the economy generates more spectacle.

## Visual bible

Royal violet and midnight plum; warm gold and ivory; jewel-pink, diamond-blue, mint, and magical lavender accents. Rounded, glossy, densely rewarding mobile interfaces. Gradient panels, small ornate labels, decorative badges, celebratory rings, jewel icons, confetti, and unabashed exclamation marks. The visual language should be *immaculately consistent*, never deliberately ugly. Satire is strongest when the product looks expensive and entirely convinced of itself.

# V. THE GRAND ECONOMIC ENCYCLOPEDIA

## Founding wallet

The initial shared progression includes **Coins, Diamonds, Stars, Energy, Crowns, and Tickets**. Other specialized quantities and prestige instruments arrive as the empire expands. These balances are fictional and persisted locally. Some are universal; others are subsystem-specific.

## Six reserve families, eight denominations each

### 👑 Royal Tender
**Crowns · Lesser Crowns · Crown Shards · Crown Dust · Royal Seals · Sovereign Marks · Imperial Pennies · Crown Futures.**

Royal Tender is the official language of monarchy, land, ceremony, and fiscal legitimacy. Crown Dust is the inevitable result of repeatedly dividing a perfectly good Crown. Crown Futures permit citizens to be optimistic about crowns they have not yet earned.

### 🔮 Arcane Capital
**Mana · Greater Mana · Mana Shards · Ether · Ether Residue · Spellmarks · Mystic Sparks · Unspent Potential.**

Arcane Capital prices the impossible. Unspent Potential is the most philosophically honest asset in the realm, because its value increases the longer nobody does anything with it.

### ⚔️ Martial Assets
**Valor · Honor · Glory · Battle Marks · Victory Fragments · Heroic Essence · Campaign Seals · Tactical Prestige.**

These are awarded for heroic deeds, strategic participation, and the ability to win battles with no possibility of defeat. A Victory Fragment is not evidence of a partial victory; it is a whole victory subdivided for accounting convenience.

### 💖 Affection Instruments
**Hearts · Friendship · Loyalty · Admiration · Devotion · Companion Bonds · Warmth · Tiffany Favor.**

The realm's most emotionally liquid market. Companion Bonds are simultaneously evidence of love and an investment product. Tiffany Favor is the benchmark asset against which all other feelings are measured.

### ⏳ Temporal Securities
**Seconds · Saved Seconds · Bonus Minutes · Time Shards · Chrono Dust · Tomorrow Tokens · Yesterday Credits · Pending Eternities.**

Time is both a resource and an accounting problem. Yesterday Credits are suitable for refunds issued in prior fiscal years. Pending Eternities mature eventually, in a manner of speaking.

### 🌟 Prestige Derivatives
**Prestige · Greater Prestige · Prestige Shards · Legacy · Ascension · Transcendence · Rebirth Credits · Prestige Prestige.**

Prestige Prestige is what happens when an empire runs out of meaningful ways to say Prestige. This is not a defect; it is a roadmap.

**Total:** 48 reserve denominations, in addition to the founding wallet and subsequent specialist credits. Conversion uses fictional reference rates and a ceremonial spread. The Royal Reserve Bank supports vault inspection, grants, exchange, conversion, accounts, audits, receipts, and Tiffany's advice.

## The Royal Reserve Bank

The bank exists to transform simple rewards into ornate financial obligations. Central-bank grants distribute multiple denominations. Audits certify financial magnificence. Exchanges impose spreads. The account ledger remembers transactions. A user can be both wealthy and in need of an immediate emergency liquidity celebration.

## Department of Rewards

Rewards generate receipts. Receipts generate claimable rewards. Claims generate new paperwork and further Prestige Shards. The receipt is the unit of bureaucratic reproduction. In a mature economy, the receipt may become more valuable than the event it records.

## Everything Factory and Universal Supply Chain

The Great Convergence established a cross-game supply-chain presentation, universal objectives, factory production, and an exchange. Its initial stages include ceremonial advancement; **not all supply-chain stages are automatically driven by underlying game actions**. The roadmap must connect actual production, construction, battles, pet bonds, and planetary actions to stage completion rather than pretending this wiring is finished.

## Stock Exchange

Eight fictional listed securities: Royal Keep Futures; Dragon Egg Holdings; Tiffany Favor Bonds; Match 1 Victory Fund; Frozen Warmth Energy; Heroic Inaction Group; Galactic Real Estate; Evermore Parent Holdings. Users buy and sell using fictional coins; holdings and prices persist. Gameplay and institutional events can affect prices. Dividends are payable. **This is a simplified game mechanic, not a realistic order-book exchange.**

# VI. THE AGE OF INSTITUTIONS

## Royal Marriage Market

Every wedding joins two named nobles, creates a dynasty, appoints an heir a duke, and yields tax consequences and companion-bond rewards. Dynastic entries persist. The present generator is intentionally compact; full genealogical genetics, intergenerational marriages, legal succession, and family trees belong to the roadmap.

## Evermore Revenue Service

Form 1040-MORE guarantees the player has overpaid. Refunds arrive in Yesterday Credits. Tax credits accrue from selected events. The system records filings and refunds, but a comprehensive progressive tax engine spanning every denomination is future work. The institution's moral principle is simple: refunds are taxable, but the refund tax is refundable.

## Parliament

Twenty-four seats represent twelve game-worlds. Citizens vote on proposed laws. Every proposal passes 24–0 regardless of the citizen's vote, which is nevertheless thanked for its meaningful participation. Enacted legislation persists in the statute book. The first bills concern gem classification, builders, Tiffany, dragon egg officeholders, financial clarity, and victory rights. **Broad mechanical effects of each law are still an expansion opportunity.**

## Evermore University

Research Knowledge is earned from institutional events. Eight programs consume it: Advanced Gem Recognition, Accelerated Construction, Dragon Appreciation, Economics of More, Tiffany Studies, Temporal Efficiency, Applied Democracy, and Applied Victory Studies. Research ranks persist. The doctorate is awarded for pursuing a field in which failure is impossible. Research currently functions mainly as progression and ceremony; more systemic consequences are planned.

## Department of Existential Necessity

The department reviews proposed features. All are essential. Every approval generates additional administrative requirements. Its growing registry is a monument to the impossibility of ever being finished. The logical end state is an audit of the department itself, which will be unanimously approved.

## Tiffany's Office of Universal Governance

Tiffany serves as Prime Minister, central banker, chief justice, university chancellor, wedding officiant, and CEO. Royal decrees can affect specific balances and create event records; some effects are narrative. The office's constitutional position is unambiguous: Tiffany is accountable to Parliament, whose representatives were appointed by Tiffany.

## Universal institutional event stream

An inspectable, locally persisted sequence connects certain game rewards and institutional actions to market prices, research knowledge, tax credits, and other balances. The event log is bounded for mobile storage. **Not every action in every game has yet been connected; this is the critical integration frontier.**

# VII. PARTICLE INDUSTRIALIZATION

## The Festival

The particle engine creates contextual bursts, emoji and glowing dots, confetti ribbons, expanding rings, and rain. Match taps, bank activity, ceremonies, weddings, votes, research, and decrees are among its triggers. DOM particles are bounded and removed after their animations; reduced-motion preferences are respected. A mobile device should experience excess without retaining thousands of permanent nodes.

## Six Foundries

Sparkles, Glitters, Twinkles, Shimmers, Confetti, and Premium Confetti have their own production factories. Each supports factory-level upgrades and unionized worker hiring, both using fictional coins. Manufacturing creates aggregate output, an event in the registry, and a corresponding celebration. Premium Confetti is indistinguishable from ordinary confetti; its superiority is contractual.

## Ministry of Reclamation

Produced particles can be reclaimed into Dust. Dust refines into Essence. Essence mints Particle Credits. Each transformation produces its own celebratory particle event, ensuring the ministry can never entirely reduce the supply of particles. This is **the Reclamation Paradox**.

## Royal Weather Bureau

Ordinary Sunshine, Glitter Storm, Gold Rain, Diamond Hail, Heart Showers, and Bureaucratic Fog appear as forecast states. Weather events generate visual effects and production records. The forecast is 100% confident and 0% accurate. **True gameplay-wide weather modifiers remain planned, not shipped.**

## Particle Rights Tribunal

A representative particle can bring suit for premature despawning, unpaid glitter overtime, unlawful recycling, inheritance, or misclassification. Tiffany adjudicates. Cases and outcomes are recorded. The tribunal is currently a satirical procedural generator, not an adversarial simulation.

## Great Particle Census

Every production event increases aggregate counts and creates a **representative named registry entry**: royal title, serial, birthplace/source, dependents, and tragic lifespan. The system does **not** store an individual permanent record for each ephemeral rendered DOM particle; this distinction is intentional for mobile performance. Representative records are bounded while aggregate counts persist.

## Retirement System

Particle Credits fund the pension system. Retirement age: 65 years. Expected particle lifespan: 1.4 seconds. The fund's theoretical solvency is therefore extraordinary. Tiffany considers the absence of living claimants a testament to excellent governance.

# VIII. LORE BIBLE: THE TIFFANY DOCTRINE

**Tiffany is not a mascot who appears in every game. Tiffany is the only truly persistent institution in Evermore.**

She changes wardrobe and title, but never conviction. She believes that all actions are victories, all systems are essential, all financial positions are strong, all legislation is popular, all scientific discoveries are profound, and all particles have enjoyed full lives. She is never knowingly cruel. She is genuinely, almost cosmically delighted.

# XII. ENGINEERING & OPERATIONS CONTRACT

## Current architecture

A self-contained static HTML/CSS/JS experience served through GitHub Pages, with a shared global state and browser-local persistence. It is a fast experimental JIT website, not a production multiplayer service. The original UI and successive feature phases have been added incrementally, and the resulting script contains several layers of wrapped render, navigation, reward and celebration functions.

**Strengths:** extremely rapid iteration; one deployable file; no server; no authentication; immediate mobile access; a shared state and visual grammar; lightweight particle rendering.

**Risks:** growing single-file complexity; function wrapping and ordering dependencies; broad mutable global state; accidental duplicate effects; incomplete cross-game event wiring; limited automated testing; browser-local data loss; performance cost from large DOM updates and repeated particle events.

## Prioritized technical debt

1. **Regression test the entire navigation tree**, including home, catalog, all twelve games, bank, government, particle industry, and hash navigation after refresh.
2. **Verify bank denomination identifiers** and every conversion/grant/receipt path; protect against missing state fields and malformed older saves.
3. **Consolidate event emission** so one gameplay action produces one authoritative semantic event and downstream institutions subscribe to it.
4. **Avoid duplicate particle accounting** when a ceremony wraps an action that already produces particles.
5. **Make economic conservation explicit:** define issuance, sinks, conversion spread, minting, reclamation, and stock trades.
6. **Separate visual particles from economic particles:** distinguish sampled display events, manufactured quantities, and named registry representatives.
7. **Protect mobile performance:** bounded particle count, bounded event history, responsive layouts, 44px-ish tap targets, and no unintended horizontal scrolling.
8. **Harden persistence:** versioned save migrations, export/import, recovery from corrupted localStorage, and reset confirmation.
9. **Add deterministic tests** for financial arithmetic, event propagation, dynasty creation, taxes, legislation, and particle production.
10. **Document feature flags and unfinished wiring** instead of silently representing narrative effects as implemented mechanics.
11. **Audit accessibility:** keyboard focus, contrast, reduced motion, readable currency numbers, and announcements for important results.
12. **Create a single institution registry** rather than perpetually stacking unrelated function wrappers.

```js
  time: "2026-10-14T01:15:36Z",
```

```text

    ↓
```

### XVIII-E. MATCH i™ — Unreal Engrams

**Route:** [`#matchi`](https://bonoj.github.io/jit/evermore/#matchi).

This was the conceptual counterattack to Infinity: not a larger quantity, but a **different number system**. The imaginary unit `i` satisfies `i² = −1`. Successive powers cycle:

```text
i¹ =  i       imaginary credit
i² = −1       real liability
i³ = −i       imaginary reversal
i⁴ =  1       real restitution

i + (−1) + (−i) + 1 = 0
```

Four icons—`1`, `i`, `−1`, and `−i`—orbit a stationary jewel. Each jewel tap advances the wheel by 90 degrees; the cycle counter increments every fourth match. The on-screen imaginary balance is presented as a zero-net conceptual ledger; it is **not** a fully implemented transaction-by-transaction complex-number balance sheet.

The naming is the joke's second layer. An engram is a memory trace; an *unreal engram* is a trace of an event that never occurred. It is a natural sibling to the retroactive victory bureaucracy and the Royal Bank's willingness to finance fictional certainty.

### XVIII-G. The treasury incident and its engineering lesson

The user reported a concrete defect: **Match 33's apparent rewards did not appear in the main currency counter**. The investigation identified the actual shared-wallet API:

```js
function reward(coins=0,stars=0) {
  state.coins += coins;
  state.stars += stars;
  state.xp += Math.max(1,Math.ceil(coins/15));
  // Level-up logic...
  save();
  wallet();
}
```

The canonical shared save is `evermore-save-v1`. Isolated per-game `localStorage` keys are for game statistics, not the universal treasury. The fix explicitly wired Match 33 and Match 1 3D to shared rewards, and ensured the twelve expansion-game win handler calls `save();wallet()` after updating shared coins/stars. Original games already use the shared reward pathway.

**Important qualification:** the correction was verified at source level, not through a complete browser-based regression across every game, every currency, and every persistence boundary. Do not describe “all games correctly generating currencies” as a fully proven fact. Future QA should verify (a) displayed win, (b) actual wallet delta, (c) reload persistence, (d) spending and negative-balance rules, and (e) no double-award from repeated taps. Different mini-games have different reward profiles; not every game must produce every currency.

**Known historical limitation:** wins earned in Match 33 *before* the shared-wallet fix remain recorded in its per-game counters but were not automatically backfilled into the shared treasury. A migration/backfill would require explicit design to avoid double-crediting.

# XIX. THE FACTORY THAT MANUFACTURES ITS OWN FACTORIES
## EVERMORE GENERATOR™ — Recursive Product Development, 2026-10-14 UTC

**Implementation:** [`b744170d`](https://github.com/bonoj/bonoj.github.io/commit/b744170d5fca179c3ec824f69975a33b63e0f13a) · **Route:** [`#generator`](https://bonoj.github.io/jit/evermore/#generator) · **Source:** `jit/evermore/index.html`.

### XIX-A. Tiffany's authorization

After MATCH i's conjugate acquired a rotating gemstone, the product team asked the obvious question: **what if Evermore generated Evermore inside itself?** Tiffany's decision was immediate: *“Ship it.”* The first factory is now committed to the site. It is not a mockup or an inert list of titles. It creates game instances with actions, win thresholds, progression, persistence, and actual deposits into the shared Evermore wallet.

The joke has become an architectural direction. Instead of writing a bespoke page for every escalating premise, the empire can combine a **mechanic**, a **dimension**, and a **subject** into a new product. A product may then found its own subsidiary, whose products may found further subsidiaries. Every additional corporation has a fully qualified bureaucratic identity; all share one very overworked treasury.

### XIX-B. The generation grammar

The v1 factory draws deterministically from seven values in each of three categories:

| Axis | Options |
|---|---|
| Mechanic | MATCH, MERGE, TAP, IDLE, ROTATE, REMEMBER, GENERATE |
| Dimension | 0D, 1D, 2D, 3D, −1D, iD, ∞D |
| Subject | GEMS, DRAGONS, ENGRAMS, CROWNS, PENSIONS, PARTICLES, GENERATORS |

The name format is `<MECHANIC> <DIMENSION> — <SUBJECT>™`. A subject-specific emoji appears as the playable central target. The seed also determines the win threshold and reward amount. There are **343 nominal title combinations**, though different seeds may produce the same combination with different thresholds and payouts; this is **not** 343 independent mechanics or 343 different implementations.

```js
function egBlueprint(seed) {
  let m = egHash(seed,1)%7;
  let d = egHash(seed,2)%7;
  let q = egHash(seed,3)%7;
  return {
    seed, m, d, q,
    title: egMechanics[m]+' '+egDimensions[d]+' — '+egSubjects[q],
    icon: egIcons[q],
    target: 3+(egHash(seed,4)%8),
    reward: 40+(egHash(seed,5)%8)*20
  };
}
```

**Determinism:** `egHash(seed,k)` is an unsigned 32-bit integer mixing function using XOR, multiplication with `Math.imul`, and bit shifts. The same seed and category selector reproduce the same blueprint without storing the full generated definition. Seeds are currently sequential positive integers; generated content is reproducible from the current code version, but the algorithm is **not yet versioned for forward compatibility**.

### XIX-C. The actual gameplay contract

The generated game displays its three reels, title, seed, depth, victory count, central gem/subject button, progress bar, and action button. Both playable buttons invoke the same `egAct()` handler. Each action increments the game's progress counter. At the seed-specific target, the progress counter resets and a victory is recorded.

- **Win threshold:** 3–10 actions, inclusive.
- **Coin reward:** 40–180 coins per win, in increments of 20.
- **Stars:** one per win.
- **Diamond bonus:** one additional diamond on every fourth win *for that generated game*.
- **Wallet integration:** `reward(b.reward,1)` deposits coins and stars, and already saves and refreshes the wallet. The fourth-win diamond is added to `state.diamonds` and explicitly saved/refreshed.
- **Game state:** `steps`, `wins`, `seed`, `depth`, and optional `parent` persist independently of the universal wallet.

**Truth in advertising:** the labels MATCH, MERGE, IDLE, ROTATE, REMEMBER, and GENERATE are *currently generated themes*, not seven distinct simulation algorithms. In v1 all products use the same tap-to-progress gameplay primitive. This is a working procedural game *configurator*, not yet a full mechanic-composition engine. The future architecture should make those verbs mean genuinely different actions.

### XIX-D. The subsidiary recursion

`egCreate()` creates a top-level product, assigning the next integer seed, initializing its counters, selecting it, and persisting the catalog. `egSpawnChild()` creates another independently playable product with a fresh seed and a `parent` reference to the selected game's seed. Its depth is parent depth plus one, capped at 99 for display/state. The new subsidiary becomes the active game immediately.

```text
EVERMORE
└── GENERATOR
    ├── GAME #1 (depth 0)
    │   └── GAME #3 (depth 1, parent #1)
    │       └── GAME #4 (depth 2, parent #3)
    └── GAME #2 (depth 0)
```

This hierarchy is stored as flat records with `parent` and `depth`; **the current catalog is a flat list**, not an interactive tree visualization. A subsidiary does not run a separate copy of the entire Evermore website, generate arbitrary JavaScript, or deploy new pages. The recursion is **data-driven within one shared executable runtime**. The UI lists the most recent 60 games; older games remain stored but are not directly selectable through that limited catalog view.

The factory's two top-level buttons, **GENERATE A GAME** and **GENERATE EVERMORE**, currently both call `egCreate()`. The latter is a theatrical promise of future recursive world-generation, not a separate full-site generator.

### XIX-E. Persistence and treasury boundaries

The factory stores its own catalog in `localStorage['evermore-generator-v1']`, with a record shaped like:

```json
{
  "next": 5,
  "selected": 3,
  "games": [
    {"seed":1,"steps":2,"wins":0,"depth":0},
    {"seed":2,"steps":0,"wins":1,"depth":0},
    {"seed":3,"steps":0,"wins":2,"depth":1,"parent":1},
    {"seed":4,"steps":1,"wins":0,"depth":2,"parent":3}
  ]
}
```

This is an illustrative schema, not a claim about any particular player's save. The shared Evermore treasury remains `evermore-save-v1`. Generated wins call the existing `reward()` pathway, preserving coins, stars, XP, level-up behavior, and wallet refresh. The generator never inserts `Infinity`, complex numbers, or ceremonial currencies into the spendable numeric wallet.

**Failure boundaries:** browser storage is local to the device/browser; no account sync, server persistence, cloud generation, or external commerce is implied. The factory currently catches storage exceptions rather than presenting a save-failure warning. The catalog has no deletion, export, import, or seed-version migration interface.

### XXI-C. Filing, resolution and causal branching

The player can open a case with **FILE AN INCIDENT**, which cycles through the eight incident types using the next case ID, or file a specific type through the **INCIDENT ORIGINS** buttons. A newly opened case receives a monotonically increasing integer ID, type index, status `open`, source, timestamp and `resolution:-1`.

Each open case offers four responses. `eiResolve(id,choice)` verifies that the case exists and is open, then marks it resolved and records the selected choice. The four response indices share common **mechanical outcomes** across all eight incident types:

| Choice index | Narrative response | Mechanical result |
|---|---|---|
| 0 | Settlement / preservation / recognition, depending on incident | Case resolves; `reward(12,1)` awards 12 coins and one star |
| 1 | Referral / deeper investigation / audit | Case resolves; a new incident is opened |
| 2 | Mediation / permit / appointment | Case resolves; `reward(12,1)` awards 12 coins and one star |
| 3 | Generate replacement / new bureaucracy | Case resolves; a new incident is opened |

Follow-up incident type is computed as `(c.type + choice + 1) % eiTypes.length`. The follow-up's source records `Resolution of case #<id>`, giving a minimal causal link. The administrative event ledger records both the resolution and any newly created case.

**Important limit:** the outcome sentences are currently shared by choice index, not unique to every type-and-choice combination. This means there are 32 **labeled options**, but only four common mechanical resolution patterns. Deeper authored consequences and systemic cross-game effects remain future work.

### XXI-D. RESOLVE ALL INCIDENTS™: a mathematically honest catastrophe

The **RESOLVE ALL INCIDENTS™** control snapshots all currently open case IDs, marks each of them resolved, and opens **one new case per resolved case**. The replacement's type is `(oldType + 1) % 8`, and its source names the original case. It also logs Tiffany's award for reducing administrative overhead.

If `N` cases are open before the operation, then — absent the 120-case storage cap's pruning effects — exactly `N` new cases are opened, so the number of open cases is preserved. The number of cumulative resolved records grows, and the paperwork continues. **This implementation does not cause exponential growth**, despite the Ministry's claims; the absurdity is that the outstanding workload refuses to decrease.

If there are zero open cases, pressing the button **creates** an incident about unnecessary administrative closure. This makes the button maximally self-defeating.

**No payout is awarded for mass resolution.** Its only output is paperwork, administrative history and Tiffany's undeserved commendation.

### XXI-E. Persistence, caps and performance

The engine stores `ei` in `localStorage['evermore-incidents-v1']`:

```json

    {"id":1,"type":0,"status":"resolved","source":"Citizen Petition","created":1791940000000,"resolution":1},
    {"id":2,"type":2,"status":"open","source":"Resolution of case #1","created":1791940000100,"resolution":-1}

    "📋 Case #2 opened: The Subsidiary Declares Independence",
    "⚠️ The solution to #1 has generated another incident."

```

The JSON is **illustrative**, not actual user data. `eiSave()` catches storage exceptions without a user-visible warning. The case array retains the latest **120** records; the event ledger retains the latest **70** strings. The active docket renders at most the latest **18** open cases, newest first. Other open cases can remain stored but may not be individually selectable through that view. As older records are pruned, the visible `resolved` and `open` counts reflect the retained array, **not lifetime totals**. The ID counter continues increasing.

All persistence is browser-local. There is no multiplayer, backend queue, external case service, account sync, actual regulatory filing, or email notification. The UI uses native buttons, responsive case grids and a scrollable event ledger.

### XXI-F. Treasury contract and the larger Evermore economy

For response indices 0 and 2, the engine invokes the existing shared `reward(12,1)` function. This is intended to deposit **12 coins and one star** into the Evermore treasury and preserve its usual XP/level progression. A resolution can only pay once because `eiResolve` rejects any case whose status is not `open`. The code catches reward exceptions and logs a treasury error; it does **not** roll back the case resolution on payout failure. The ledger is therefore not yet an atomic financial transaction journal.

For response indices 1 and 3, the new incident is the consequence instead of a coin/star reward. The new case is a separate, independently resolvable record. This creates a simple causal chain and a repeatable choice between immediate reward and further bureaucracy.

# XXII. EVERMORE ONE™ — THE ONE-CLICK EMPIRE AND ITS REGRESSION HARNESS

## XXII-A. Origin and the engineering realization

The proposition was to compress the entire Evermore experience into **one click**. The first conceptual answer was an extravagant orchestration: Match 33, Match i, the Generator, the Bank, the Magic Map, the Incident Engine and the Ministry would all participate in a single ceremony with a traceable receipt.

Then came the insight: **this is a regression test in disguise.** Every feature added to Evermore increases the risk of invisible breakage at the boundaries between subsystems. A one-click orchestration offers a repeatable way to inspect those boundaries. The user approved implementation and documentation with a decisive operating principle:

> **“Never spec what you can build first.”**

This is the team's new motto. It is not a ban on design or documentation. It is a preference for a small executable proof over speculative architecture, followed by accurate documentation of what actually works and what remains to be built.

## XXII-B. The released interface

The `#one` route provides a giant **EVERMORE ONE™** button, an **Inspection Mode** button, and an itemized receipt with PASS/FAIL labels, run duration, seed, UTC timestamp, and a copy-to-clipboard control. The page is reachable from the main navigation. It is responsive and uses the established additive `render()`/`nav()` wrapper pattern.

**Two deliberately different modes:**

- **PARTY MODE** mutates the player's real local Evermore state. It awards coins and stars through `reward()`, updates diamonds/crowns through `save()`, creates a generated game record, increments the ceremonial groundbreaking counter, opens an incident, and checks the wallet's coin delta. The result is a real local-state event, not an animated fake receipt.
- **INSPECTION MODE** runs a deterministic set of 11 contract and arithmetic checks. It reads and serializes current state but is intended to leave it unchanged. It does **not** invoke the original Match 33 or Match i game handlers, does not create a subsidiary, and does not pay the player. Its purpose is a fast, low-risk source-level integration sanity check in the browser.

## XXII-C. The 11 Inspection Mode contracts

| # | Check | What is actually asserted |
|---|---|---|
| 1 | Match 33 reward contract | A modeled +3,300 coin / +33 star delta |
| 2 | Match i complex cycle | Four complex positions sum to zero |
| 3 | Generator seeded recipe | Same seed reproduces same blueprint; target 3–10; reward 40–180 |
| 4 | Generator subsidiary lineage | Modeled child points to parent and increments depth |
| 5 | Royal Bank reward arithmetic | Modeled 90-coin win adds 90 coins, 1 star and 6 XP |
| 6 | Magic Map ceremonial persistence | Nine districts exist and locally stored strike count is nonnegative |
| 7 | Incident causal resolution | Eight incident types and referral index arithmetic |
| 8 | Incident bulk conservation | Modeled replacement count equals original open count before pruning |
| 9 | Matchematics invariants | Elementary zero, sign and cancellation identities |
| 10 | Save-state round trip | Serialized snapshot parses and reserializes identically |
| 11 | No permanent mutation | Snapshot before and after the inspection matches |

**Honest scope:** several checks model expected results instead of executing the corresponding production game handler. They are useful **contract checks**, but a green receipt does not prove the full site is regression-free. In particular, the check for mass-resolution conservation is a mathematical model and does not exercise the actual `eiAll()` mutation. The receipt must not be interpreted as a browser end-to-end test suite.

## XXII-D. Party Mode's six recorded operations

| Operation | Actual effect |
|---|---|
| Match 33 ceremonial payout | Calls `reward(3300,33)` and checks deposited coins/stars |
| Match i four-turn payout | Calls `reward(90,1)` four times, adds 4 diamonds and 1 crown, then saves |
| Generator subsidiary | Allocates next seed; creates a new game record with optional parent lineage; persists generator state |
| Magic Map groundbreaking | Increments `evermore-park-groundbreaking-v1` in localStorage |
| Incident opened | Calls `eiNew(2,'EVERMORE ONE Party')` |
| Royal Bank reconciliation | Verifies coin increase of at least 3,660 |

Party Mode is **not** an atomic transaction: if an operation fails, earlier operations are not rolled back. Its Match 33 and Match i entries execute the **shared reward path**, not the complete visual/gameplay victory handlers. The generator step directly creates a record with the same state schema rather than invoking the UI's `egCreate()`. The groundbreaking step directly increments the same localStorage key rather than invoking the UI's `epGround()`. The incident step **does** invoke the actual `eiNew()` function. These distinctions matter when diagnosing failures.

The coin-delta assertion is a lower bound (`>=3660`), not an exact ledger reconciliation. The party also generates normal XP/level effects via `reward()`. It is a genuine integration smoke test of several shared paths, not yet a comprehensive end-to-end orchestration.

## XXII-E. State and receipt contract

`eoLast` holds the latest result **in memory only**, and `eoRuns` counts runs during the current page lifetime. A refresh discards the receipt unless the user has copied it. Each row is constructed through `eoCheck(name,fn,rows)`, which catches exceptions and records a PASS or FAIL with a detail string. The report includes `mode`, `seed`, `rows`, `elapsed`, `build`, `time`, and `before`. The `build` field attempts to read a `[data-build]` element and otherwise records a fallback string; **the build SHA is not yet guaranteed to appear in receipts**.

The copy button uses `navigator.clipboard.writeText(JSON.stringify(eoLast,null,2))`, with a toast on success or failure. Clipboard support and permission vary by browser.

**Privacy caveat:** Inspection Mode's `before` field contains a serialized snapshot of the current player state, generator catalog, incident docket and Match i state. Copying or sharing the receipt therefore shares this local gameplay data. A future report format should redact the full snapshot by default and include only hashes, summaries or opt-in details.

# XXIII. GEMPIRE OS™ — THE MODEL-FORWARD MODEL-OPERATED EMPIRE

**Implementation:** [`e96149f5`](https://github.com/bonoj/bonoj.github.io/commit/e96149f5797734a2f172a57593adf56dbf010cee) · **Route:** [`#gempire`](https://bonoj.github.io/jit/evermore/#gempire) · **Source:** `jit/evermore/index.html` · **Committed source blob:** `94f843c74e3ddc694c166542323042c0511c9a92`.

## XXIII-A. The strategic pivot

After EVERMORE ONE turned a single-click experience into a rudimentary regression harness, the next idea was to make Evermore a **model-forward, model-operated GEMPIRE™**. The distinguishing principle is *operation*: the model should not merely describe the games, banks, ministries, generator and theme park. It should discover capabilities, inspect live state, issue typed commands, receive structured receipts, verify consequences and decide its next action.

The user reaffirmed the project's working motto: **Never spec what you can build first.** The first implementation therefore provides a functioning local operator console and instrumentation before introducing any remote language-model integration.

**Honest boundary:** GEMPIRE OS v0 is a **browser-local command operating surface**, not a language model, hosted agent, API server, autonomous worker or self-modifying code generator. The command registry is designed for a future model adapter. It currently requires a person to enter/select a command and click Execute.

## XXIII-B. Executable system architecture

```text
GEMPIRE OS™ (#gempire)
  ├── Observatory → gosSnapshot()
  │   ├── wallet: coins, stars, diamonds, crowns, XP, level
  │   ├── generator: count, next seed
  │   ├── incidents: open count, retained total, next case ID
  │   ├── park: local groundbreaking count
  │   └── Match i: turns and completed cycles
  ├── Registry → gosRegistry
  │   ├── read-only commands
  │   └── mutating commands
  ├── Executor → gosExecute(name,args)
  │   ├── validate command and argument object
  │   ├── capture before snapshot
  │   ├── execute actual local operation
  │   ├── catch failure and capture after snapshot
  │   └── emit receipt
  └── Instrumentation → gos.events
      ├── sequence ID and UTC time
      ├── command, arguments, mutability
      ├── elapsed milliseconds, success/error
      ├── before and after state
      └── command result
```

The system uses the same additive route architecture as the rest of Evermore, with `render()` and `nav()` wrappers. It provides a live snapshot panel, editable JSON console, command selection buttons, a structured last-receipt view, a copy control and recent trace history.

## XXIII-C. Nine initial commands

| Command | Mode | Actual implementation |
|---|---|---|
| `os.inspect` | Read | Return a bounded live snapshot of major subsystems |
| `os.tools` | Read | Return names, descriptions and mutation flags from the registry |
| `os.audit` | Read* | Invoke existing EVERMORE ONE `eoInspect()` and return check results |
| `generator.create` | Write | Allocate seed, optionally attach a parent by seed, persist a new playable game |
| `incidents.file` | Write | Validate type 0–7 and call production `eiNew()` |
| `incidents.resolve` | Write | Validate open case ID and choice 0–3; call production `eiResolve()` |
| `park.groundbreak` | Write | Increment the existing local ceremonial counter |
| `wallet.inspect` | Read | Return current treasury balances |
| `os.trace` | Read | Return the most recent 20 instrumented receipts |

*The `os.audit` command runs the existing non-mutating audit and updates its in-memory audit receipt and page render. It is read-only with respect to the game's permanent economy, but not literally free of UI/in-memory side effects.*

**Example operator request:**

```json
{"command":"generator.create","args":{"parent":1}}
```

**Example read-only request:**

```json
{"command":"os.inspect","args":{}}
```

**Command arguments:** `incidents.file` accepts `type` (integer 0–7); `incidents.resolve` requires `id` and `choice` (integer 0–3); `generator.create` accepts optional `parent` as a seed number. The executor rejects unknown command names and non-object argument payloads. Individual commands perform additional validation as needed. The interface exposes mutability labels; it does **not yet enforce a formal permission system, approval policy, schema registry or transactional isolation**.

## XXIII-D. Instrumentation, provenance and persistence

`gosExecute()` captures `gosSnapshot()` before and after the command, times execution with `performance.now()`, assigns a monotonically increasing sequence number, records the current ISO timestamp and returns a receipt with `command`, `args`, `mutates`, `ok`, `elapsedMs`, `before`, `after`, `result` and `error`.

Receipts persist under `localStorage['evermore-gempire-os-v1']`. The latest **40** receipts are retained, and the UI shows the latest **12**. The `os.trace` command returns the latest **20**. `gosLast` is the latest receipt in memory; it can be copied as JSON using the browser clipboard.

**Privacy and capacity:** receipts include local gameplay state and user-supplied command arguments. Sharing copied traces discloses those details. This is not a secret-safe telemetry format. Large repeated receipts can consume localStorage capacity; persistence errors are currently caught without visible notification. A later release should add redaction, versioning, schema validation, bounded receipt payloads and export controls.

**Important timing caveat:** the elapsed measurement covers synchronous command execution and snapshot collection, not network latency, animation completion, GitHub Pages propagation or remote model inference.

## XXIII-E. Current limits and engineering risks

1. **No model adapter yet.** No provider keys, remote inference, tool-calling loop, server or background agent is implemented. Human-triggered JSON commands are the working interface.
2. **No event bus yet.** Existing games are not universally instrumented. The OS sees and controls only registered operations.
3. **Not transactional.** A failed command may have partially mutated state. Before/after receipts expose the difference but do not roll it back.
4. **Read-only classification is declarative.** The registry's `mutates` flag is informational, not an enforced sandbox.
5. **Limited schema validation.** Several commands have manual validation; no centralized typed schema compiler or capability authorization exists.
6. **No authenticated external interface.** The operator surface runs inside the same browser origin as Evermore. Do not expose it to arbitrary remote callers.
7. **No durable replay engine.** Receipts preserve inputs and observed results, but replay against a clean deterministic state is not yet implemented.
8. **Audit scope remains limited.** `os.audit` reuses EVERMORE ONE's modeled checks and does not become an end-to-end browser suite merely by running through the OS.
9. **Storage and observability are local.** No cross-device synchronization or external log sink exists.

## XXIII-F. Verification and recommended tests

The source commit returned blob `94f843c74e3ddc694c166542323042c0511c9a92`. All **22 inline JavaScript blocks** passed syntax parsing prior to commit. The public browser route, command execution, persistence, navigation, and mobile layout have **not** been independently exercised end to end.

Recommended runtime acceptance: open `#gempire`; run `os.tools`; run `os.inspect`; inspect wallet; create a seeded game; file an incident; resolve it with both reward and follow-up paths; break ground; run `os.audit`; inspect `os.trace`; copy a receipt; reload; confirm saved game/case/counter/trace. Test malformed JSON, unknown commands, invalid IDs, disabled storage, and narrow mobile widths.

## XXIII-G. Roadmap: from console to model-operated GEMPIRE

**Next executable seam:** build a small adapter that consumes the discoverable registry, chooses commands under a bounded budget, requires explicit approval for state-changing actions, and reports receipts. Keep the model outside the authoritative state. The command executor remains deterministic and independently testable.

Subsequent phases: centralized JSON schemas and validation; a unified event bus; automatic instrumented game events; immutable transaction IDs and idempotent treasury writes; a state-snapshot sandbox for planning; deterministic replay; failure localization; safe capability scopes; compact model-readable observations; a turn-based operator loop; and finally an optional provider-backed model with a user-controlled key or securely mediated server connection.

The defining architectural rule: **the model is an operator, not the source of truth.** Evermore's state and rules remain executable without it. Every action must return evidence.

# XXIV. GEMPIRE ISSUE BRIDGE™ — EXISTING INGEST, NEW OPERATOR CHANNEL

**Implementation:** [`e056e89a`](https://github.com/bonoj/bonoj.github.io/commit/e056e89ab213d37d1e11620321e26c9607446bff) · **Route:** [`#issuebridge`](https://bonoj.github.io/jit/evermore/#issuebridge) · **Transport:** [`bonoj/Ingest/issues`](https://github.com/bonoj/Ingest/issues).

The user approved using the existing GitHub issue system for GEMPIRE OS, while preserving its usefulness for serious future projects. The first implementation adds a bridge **inside Evermore**; it does not modify Ingest or impose Evermore-specific schemas on the generic transport.

## Existing transport evidence

The existing Ingest repository already contains observer reports in GitHub Issues #1–#3. They carry fenced JSON observations with IDs, timestamps, sources and scene details; one contains a GitHub-hosted JSON attachment. These are observation messages, **not** GEMPIRE commands. The bridge introduces a distinct opt-in protocol marker rather than trying to execute legacy observer reports.

## Mission envelope

```json
{
  "protocol": "gempire-command-v1",
  "id": "mission-example",
  "command": "os.inspect",
  "args": {}
}
```

The issue body must contain a fenced `json` block with this protocol marker, a command string, and an argument object. The browser fetches a **public** issue from `https://api.github.com/repos/bonoj/Ingest/issues/{number}`, rejects pull requests, parses the mission, and checks that the command exists in the current `gosRegistry`. Import **never executes** the command.

## Three-stage workflow

1. **Create mission:** select a registered command and open a prefilled GitHub new-issue form in a new tab. The user must submit the issue while signed in to GitHub.
2. **Fetch and review:** enter its issue number in the bridge. The browser fetches and displays the command JSON and read/write classification. A separate **AUTHORIZE AND EXECUTE** button invokes `gosExecute(command,args)` against the local Evermore state.
3. **Return evidence:** copy the execution receipt as fenced JSON suitable for a GitHub issue comment. Posting the comment remains a **manual** step; the browser has no GitHub write credential.

Receipts include command metadata, elapsed time, success/error, and before/after state snapshots. The bridge also annotates the latest in-memory receipt with the Ingest repository, issue number, issue URL and protocol. **Limitation:** the transport annotation is applied after `gosExecute` has persisted its receipt; therefore the stored trace may not retain the added transport metadata. Future work should include provenance inside the executor before persistence.

## Security and limitations

The bridge deliberately does **not** auto-poll, auto-execute, run background tasks, authenticate to GitHub, connect to an LLM, or write issue comments. It reads public issue bodies using unauthenticated GitHub API access, subject to network/CORS behavior and API rate limits. The user must explicitly approve execution after review. GitHub is the mission/receipt transport; browser-local Evermore remains authoritative for gameplay state.

The mission parser checks the protocol marker and basic argument shape; individual registered commands provide their own validation. It does not verify the issue author's identity, sign payloads, enforce capability scopes or guarantee transaction rollback. Do not treat a GitHub issue as inherently trusted. Private issue access is not supported by the browser's unauthenticated fetch.
