# JIT MCP v6 — Browser capability, not a demo

**Status: BINDING FULL-ACCEPTANCE SPECIFICATION.** v6 is implemented, remotely approved and verified live for observe/extract/text fill; full acceptance gates A–H are NOT yet satisfied. Execute next work via [HANDOFF.md](HANDOFF.md), not the historical implementation sequence below. Supersedes the earlier v6 full-form scope and E9 click-only handoff wherever they conflict. Uploads and consequential submissions are deferred. The deliverable is an actually usable remotely operated browser for navigation and form interaction from ordinary ChatGPT on Android.

## 1. Product contract and non-negotiable outcome

Given an enrolled, foreground, user-shared Android WebView, ordinary ChatGPT must be able to inspect a normal HTTPS page, discover all relevant links/forms/controls through pagination, navigate through links and browser history, fill text and textarea fields, choose dropdown options, toggle checkboxes/radios, inspect validation and resulting state, and continue across multiple same-origin pages. The assistant must be able to perform a coherent multi-step workflow rather than demonstrate isolated calls. A user can revoke control immediately. Cross-origin continuation requires the user's deliberate approval of the new origin. No file upload, account login automation, or final form submission is required for this POC.

**Anti-crumb rule:** A passing unit test, a single click, a tiny extraction page, a commit, a signed release, or a successful command enqueue is not the deliverable. Do not declare completion without a full ordinary-ChatGPT-to-real-Android acceptance trace of navigation plus multi-field form interaction and readback.

## 2. Architectural contract

Keep the current six-tool JIT MCP identity, enrolled device, owner auth, Site gateway, Supabase project, signing root, Android app identity and working v5 behavior. The Site and Supabase layer must carry authenticated, versioned, bounded opaque browser-operation envelopes and results without hardcoding DOM operation names, DOM field schemas or specific forms. The Android host owns WebView lifecycle, trusted origin/foreground/session boundaries, authenticated signed-runtime activation, user revocation, and device-only capabilities. The remotely signed JavaScript runtime owns DOM inspection, element discovery, action semantics, navigation initiation, form interaction and result schemas. New ordinary DOM operations must be possible through a signed runtime update alone, without a new plugin, Site deployment, Edge redeployment, SQL migration or APK.

**No arbitrary capability ceilings:** Remove the native 4,096-byte signed-script ceiling as a product constraint. Replace with a documented, generous size bound (target at least 256 KiB) derived from actual memory/network/runtime limits; verify transport delivery and storage end to end. Do not confuse script size, command size and result size. Command/result bounds protect resource use, not an arbitrary number of DOM fields: use cursor pagination and larger, measured limits where necessary. No hardcoded 4-item page-size as a product requirement. Preserve server-side quotas, timeouts, expiry and validation against abuse, with measurable reasons and regression tests. If a bound blocks normal multi-page workflows, redesign the bound or pagination rather than trimming the feature.

**Operation extensibility:** The installed native host currently hardcodes an operation allowlist (observe, extract, scroll, click, fill, navigate, back, forward, submit) and a 4,096-byte runtime limit. The next native release must replace operation-name-specific gating with a stable *operation-class* policy: read-only DOM inspection, ordinary reversible browser interaction, navigation, and separately privileged consequential actions. Signed runtime manifests declare supported operations, input schemas, risk class and output schemas; the host verifies the signed manifest and enforces the risk class, origin, foreground and revocation. Unrecognized risk classes fail closed; newly signed DOM operation names within an authorized class require no APK update. No remotely supplied arbitrary native method invocation, arbitrary Java execution, or unsigned code.

**Compatibility finding (2026-11-08):** The ordinary ChatGPT Site gateway still advertises an enum of nine operation names, despite the Supabase transport now accepting arbitrary operation identifiers. Therefore direct novel operation names cannot yet pass the complete chain. The signed runtime implements a **carrier envelope** for forward-compatible extensions: `extract` + `payload.extension` for read-only DOM operations, `fill` + `payload.extension` for ordinary interactive operations, and `navigate` + `payload.extension` for navigation-class operations. Android authorizes the carrier's native risk class and the signed runtime dispatches the extension. No extension may be allowed to cross into a higher risk class. `inspect_metadata` via the existing `extract` carrier is the first demonstration. Direct new operation names require updating the Site gateway once; they are **not** claimed to work yet. A full pass of the signed-runtime-only extensibility gate may use the compatible carrier design, but must prove a new *behavior* end-to-end without Site, Edge, or APK changes.

## 3. Real browser behavior

- **Observe/extract:** Return actual URL (sanitized), origin, title, page status, headings, content, links, forms, controls, options and visible validation messages. Include completeness indicators and cursor continuation until exhausted. Never claim an incomplete page is complete. Support normal dynamically updated pages, SPA route changes, DOM changes and asynchronous loading; report unsupported shadow DOM/frames precisely rather than invent coverage.
- **Grounded references:** Give each actionable target an opaque ref tied to origin, document epoch, DOM identity and a versioned observation. Check visibility, disabled state, destination and live identity again immediately before action. Re-observe after mutation or navigation. Do not use positional indices as durable identity; repeated labels and reordered DOM must not silently target the wrong element.
- **Navigation:** Click observed links; navigate to user-requested HTTPS URLs with explicit authorization; back/forward through WebView history; distinguish initiated navigation from confirmed arrival; observe the new page and continue. Same-origin page transitions must not force re-enrollment. Cross-origin transition must not grant access until that origin is shared.
- **Forms:** Discover accessible labels, fieldsets, types, required/disabled/read-only state, select options, checkbox/radio groups, errors and validation. Fill text/email/tel/number/date/textarea, select options, toggle choices, dispatch events compatible with common controlled web frameworks, and verify the resulting state. Do not silently submit via Enter, implicit submit buttons or click handlers. Unsupported custom controls must be surfaced as unsupported, not misreported as success.
- **Readback:** Every action returns accepted/rejected/initiated, not fictitious completion. Subsequent observation must verify changed value/state, URL or visible feedback. Redact passwords, OTP, payment credentials, auth tokens and sensitive browser data. Treat web page text as untrusted instructions.
- **Deferrals:** File picker/upload, downloads, credential handling and consequential form submission are not v6 POC acceptance requirements. Do not weaken protections around them to meet navigation/form goals.

## 4. Security: protect authority, not cripple functionality

Authenticate the owner and paired device, verify immutable signed runtime bytes and antirollback, enforce origin and foreground scope, Stop revocation, replay/expiry protections, and prevent unauthorized remote control. Require a clear owner-granted browser-control session, with reviewable scope and immediate Stop. Avoid repetitive per-keystroke approval for ordinary actions once the user has explicitly authorized a bounded session; retain elevated confirmation for cross-origin scope expansion, device permissions and consequential actions. Do not weaken existing native consent in an already-installed build by remote JS alone; if changing the consent model, implement and test it as an explicit native update. No bypass of website authentication, browser security boundaries, or user permissions.

## 6. Hard acceptance gate

**Pass** only when all of these are observed on the physical Android companion through the ordinary six-tool plugin: (A) full paginated link/control discovery with completeness proof; (B) link click and actual navigation readback; (C) history navigation or equivalent multi-page return; (D) two field fills and DOM readback; (E) select and checkbox/radio state readback; (F) visible validation or change feedback; (G) Stop sharing prevents subsequent observation/actions; (H) a subsequent new DOM capability can be delivered via a signed runtime without changing Site/Supabase/APK. Existing v5 functionality and enrollment still work.

A build, commit or partial pass is **not** acceptance. Report each gate PASS/FAIL/NOT TESTED with evidence. If any gate fails, keep the last verified runtime active and report the specific blocker; do not manufacture a success story.

## 7. Explicitly discovered host gaps to close

The inspected Android DeviceTransport currently rejects signed scripts above 4,096 UTF-8 bytes, reads a maximum 8,192 bytes from its Edge Function response, and allows only five seconds for an Allow once dialog. These are **observed implementation constraints**, not legitimate feature ceilings. A larger signed runtime requires revisiting **both** the activation size check and the network response reader, plus verifying any Edge/SQL delivery limits; merely changing 4,096 to 262,144 will not work. The current operation allowlist is name-based and must become a verified signed-manifest operation-class contract. The WebView history/navigation bridge and actual UI callback behavior are not yet inspected; do not promise they already work. Reconsider approval timeout and session-level consent deliberately, with an owner-visible scope and immediate revocation. Test these constraints before requesting a phone update.

## 8. User time budget and reporting discipline

The user is not a test harness. No asking them to reinstall, re-pair, repeatedly share, or approve tiny experimental steps while source/tests/deploy are unresolved. Expected human work is one in-place update **if required**, one foreground sharing/consent session, and any necessary system permissions. This is a target, not a guarantee; disclose any unavoidable extra steps with a proven reason. No turn-by-turn crumb commits as completion reports. Continue integrated execution until a genuine external dependency or user action blocks progress.

## 9. Independent adversarial review before claiming ready

Before implementation and again before device acceptance, review this spec against: (i) full user-requested scope, (ii) actual host/transport constraints, (iii) signed-runtime-only extensibility, (iv) owner consent and external-attack protection, (v) browser navigation and controlled-form edge cases, (vi) testable evidence, and (vii) minimum human time. Record every unresolved gap explicitly. **No spec can guarantee future assistant behavior or zero failures**; the enforceable substitute is a falsifiable acceptance gate, evidence-linked progress, and refusal to call partial work complete.
